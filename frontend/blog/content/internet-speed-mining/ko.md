Blocknet 채굴 작업을 전달하는 연결을 재현 가능한 순서로 확인하세요. 로컬 해싱과 네트워크 통신을 구분하고 중단을 기록하며 한 번에 한 네트워크 조건만 비교합니다. 이 가이드는 bntpool.com에 접속하는 채굴기를 다룹니다. 채굴기 다운로드나 블록체인 전체 노드 동기화는 별도 작업이므로 따로 측정해야 합니다.

## 연결이 빨라지면 채굴도 빨라지나요?

<Answer>
다운로드 대역폭이 늘어도 CPU나 GPU가 계산하는 해시가 직접 늘어나지는 않습니다. 풀 연결은 작업, 제출, 응답을 전달하므로 시기적절하고 안정적인 전달이 중요합니다. 인터넷 요금제를 바꾸기 전에 현재 작업, 재연결 메시지, 승인된 셰어를 확인하고 로컬 해시레이트와 풀이 추정한 제출 작업량을 구분하세요.
</Answer>

*채굴기가 네트워크 경로를 통해 풀과 작업 및 셰어 메시지를 교환하며 시계가 전달 시간을 나타냅니다.*

## 대역폭, 지연 시간, 로컬 해시레이트를 구분하세요

대역폭은 데이터 전송 용량을, 지연 시간은 전달 지연을 뜻합니다. 속도 테스트에서 용어가 섞여 보이면 [네트워크 용어 참고 자료](https://www.cloudflare.com/learning/performance/glossary/what-is-latency/)를 읽으세요. 다운로드 결과와 지연 시간 결과는 서로 다른 질문에 답합니다. 테스트 대상은 풀과 다른 경로를 거칠 수도 있으므로 각 측정의 맥락을 기록하세요.

채굴기의 H/s는 장치에서 해싱이 수행되는 양을 측정합니다. 풀은 일정 시간에 제출된 셰어로 작업량을 추정하므로 자체 변동이 생깁니다. 두 표시의 짧은 차이는 네트워크 손실을 직접 측정한 값이 아닙니다. 단위와 시간 구간은 [해시레이트 가이드](/blog/ko/what-is-hashrate/)를 참고하고 차이를 설명하기 전에 제출 결과를 모으세요.

## 채굴기와 풀 사이에서는 실제로 무엇이 오가나요?

연결된 채굴기는 로그인하고 채굴 작업을 받아 로컬에서 해시를 계산한 뒤 조건을 만족한 셰어를 보냅니다. 시도한 모든 해시를 업로드하거나 시도마다 작업 메모리 영역을 전송하지 않습니다. [Stratum 가이드](/blog/ko/stratum-mining-protocol/)는 이 메시지 교환을 따라갑니다. 작업 전달, 제출 전달, 풀 응답은 같은 연결을 쓰더라도 별개의 관찰 대상입니다.

메시지 수는 작업, 할당된 셰어 난이도, 제출, 연결 유지 메시지, 재연결에 따라 달라집니다. 따라서 특정 세션을 측정하지 않고 보편적인 월간 데이터 사용량을 제시하는 것은 적절하지 않습니다. 데이터 예산이 필요하면 대표적인 기간에 운영체제나 라우터의 장치별 카운터를 사용하세요. 기간과 다른 트래픽을 기록하고 채굴 전용 사용량을 추정할 때 다운로드와 노드 동기화는 제외하세요.

## 채굴기를 바꾸지 말고 Wi-Fi와 Ethernet을 비교하세요

무선 사용과 중단이 겹치면 가능한 경우 같은 컴퓨터를 Ethernet으로 연결해 비교하세요. 풀 주소, 채굴 백엔드, 스레드 설정, 앞에서 하는 작업은 유지하세요. 시작과 종료 시각을 기록하고 채굴기 연결 로그를 살펴보세요. 유용한 비교는 네트워크 링크를 분리합니다. 하드웨어 설정과 연결을 함께 바꾸면 원인을 찾기 어렵습니다.

대용량 업로드, 클라우드 백업, 다른 가정 내 전송이 응답 지연과 겹치는지 확인하세요. 직접 제어하는 전송을 잠시 멈춰 패턴이 달라지는지 본 뒤 복구하세요. 속도 테스트 자체도 트래픽을 더하므로 실행 시각을 기록하세요. 평소 네트워크 보호는 켜 둔 채 채굴기 실행을 허가받은 네트워크만 사용하세요.

## 어떤 관찰이 풀 연결 문제를 보여 주나요?

채굴기의 순서를 따라가세요. 엔드포인트 연결, 로그인, 작업 수신, 셰어 제출, 응답 순입니다. 로그인이 거부되면 약한 Wi-Fi라고 가정하지 말고 주소와 정확한 메시지를 살피세요. 연결이 반복해서 끊기면 시각과 주변 로그 행을 보관하세요. [추적 가이드](/blog/ko/track-your-miner-on-bntpool/)는 엔드포인트 확인과 풀 해시레이트가 0인 상황을 다루며, [상태 페이지](/status)는 서비스 상황을 알려 줍니다.

복구 후에는 새로 사용 가능한 작업과 새로 승인된 셰어를 확인하세요. 웹사이트 복구나 ping 성공만으로 채굴 세션이 이 단계를 마쳤다고 할 수는 없습니다. 반대로 브라우저 오류만으로 Stratum이 멈췄다고 볼 수도 없습니다. 각 확인이 실제 무엇을 시험했는지 기록해 공개 사이트, 채굴기 전송 연결, 풀 응답을 구분하세요.

## 늦거나 거부된 제출은 어떻게 해석하나요?

작업이 바뀔 때 전달 지연은 영향을 줄 수 있지만 거부된 셰어가 자동으로 느린 연결의 증거는 아닙니다. 이유를 읽고 작업 및 재연결 시각과 비교하세요. 중복 제출, 난이도 검사, 작업 유효성에는 서로 다른 원인이 있습니다. [셰어 결과 가이드](/blog/ko/accepted-rejected-stale-shares/)는 분류와 반복 오류에 유용한 세부 정보를 설명합니다.

잠깐 조용하다는 이유로 패킷이 손실됐다고 보지 마세요. 셰어 발견은 변동하며 할당된 난이도는 제출 빈도에 영향을 줍니다. 같은 채굴기 설정으로 대표적인 기간을 비교하고 실제 응답을 확인하세요. 로컬 해싱도 줄었다면 CPU, GPU, 메모리 활동을 별도로 조사하세요. 다른 앱이 컴퓨터를 공유할 때는 [데스크톱 채굴 가이드](https://seineminer.com/ko/blog/mine-while-using-pc/)가 도움이 됩니다.

## 간단한 기록을 남기고 개선을 검증하세요

채굴기 버전, 연결 방식, 풀 엔드포인트, 대략적인 시각, 재연결 또는 거부 메시지의 정확한 내용을 적으세요. 다른 장치도 영향을 받았는지, Ethernet 비교나 전송 일시 중지가 패턴을 바꿨는지도 포함하세요. 진단 정보를 공유할 때 계정 정보는 비공개로 유지하세요. 이런 관찰은 시각이나 대상이 없는 속도 테스트 숫자 하나보다 나은 보고가 됩니다.

한 가지를 집중해서 바꾼 후 의도한 풀과 주소가 선택돼 있는지, 작업이 도착하고 새 셰어가 승인되는지 확인하세요. 그런 다음 풀 표시 구간이 갱신될 시간을 둔 뒤 기록을 비교하세요. 평소 환경에서 안정적으로 전달되는 구성을 유지하세요. 목표는 동작을 설명할 수 있는 정상적인 채굴 연결이며, 대역폭 측정은 실제로 예산을 잡아야 하는 트래픽에 사용하세요.
